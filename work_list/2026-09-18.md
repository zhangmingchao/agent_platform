# 2026-09-18 开发记录

## 模型每日 Token 限额

### work_list

1. 为每个用户模型配置增加“不限额”和“每日限额”两种模式。
2. 新增模型每日 Token 用量表，分别记录输入、输出、总 Token 和请求次数。
3. 增加强类型的限额配置、用量、预占和状态实体。
4. 在每次 LLM 调用前估算完整消息和工具 Schema 的最大消耗，并通过 Redis 原子预占。
5. 在模型调用结束后读取真实 usage，结算 Redis 预占并持久化 MySQL 用量。
6. 将真实 Token 用量同步到 Trace Span 和 Trace Run 汇总。
7. 将限额能力统一接入普通聊天、工作流 Agent 和已保存模型的连接测试。
8. 扩展模型管理接口和前端页面，支持配置限额并查看今日使用量。
9. 补充额度校验、并发预占、结算、异常调用和跨日期统计测试。
10. 执行后端测试、前端构建、Python 语法检查和差异格式检查。

### 实现方案

- `models` 表保存 `quota_mode` 和 `daily_token_limit`，仅允许 `unlimited`、`daily`。
- `model_daily_token_usage` 按模型配置和上海时区自然日保存真实用量，不依赖定时清零。
- MySQL 保存可审计的最终用量；Redis 使用 Lua 原子完成当日额度初始化、判断和预占，避免并发超额。
- 限额 Callback 挂载到模型实例，每次 ReAct 模型轮次都会独立预占和结算；LangGraph State 不作为额度事实来源。
- 调用前按完整消息、工具 Schema、协议开销和安全系数估算输入 Token，再加单次最大输出 Token。
- 调用完成后优先读取供应商 usage；无法取得 usage 或调用异常时按预占量保守结算，防止绕过限额。
- 不限额模型仍记录真实用量，便于前端统计和后续审计。

### 影响范围

- MySQL 模型配置与每日用量表。
- Redis 模型额度预占键。
- LangChain 模型工厂、Token 估算与 Callback。
- 聊天、工作流、模型连接测试及 Trace 统计。
- 模型管理 API、前端配置表单和用量展示。

### 实现结果

- 模型配置已支持 `unlimited` 和 `daily`，旧数据默认保持不限额。
- 已按模型配置和上海时区自然日记录输入、输出、总 Token 与模型调用次数。
- 每轮 LLM 调用都会经过 Redis 原子预占；供应商返回 usage 后按真实用量结算，无 usage 或异常时按预占量保守记账。
- 普通聊天、工作流 Agent 和已保存模型的连接测试已统一接入额度 Callback，额度数据未写入 LangGraph State。
- Trace Span 和 Trace Run 已记录、汇总供应商返回的真实 Token 用量。
- 模型管理页面已支持配置每日额度，并展示今日已用和剩余额度。
- 新增 7 项额度专项测试；后端完整 81 项测试通过。
- 前端生产构建、应用导入、Python 语法检查和 `git diff --check` 通过。

## 移除 RunSkillScript 工具

### work_list

1. 删除 `RunSkillScriptInput`、执行函数和 LangChain 工具注册。
2. 简化 Runtime 工具构建参数，只保留 `ExecutePython`。
3. 删除 Skill Python脚本路径解析入口。
4. 删除仅供 Skill脚本使用的 `source_type`、`skill_id` 和 `RUNTIME_ARGS` 传递链路。
5. 从 `code_executions` 表定义中移除专用字段，并为现有空数据表增加删除字段迁移。
6. 更新 Runtime、Skill集成及项目说明文档，避免继续宣传已移除能力。
7. 增加工具注册回归测试，确认 Agent只能获得 `ExecutePython` Runtime工具。
8. 执行后端完整测试、Python语法检查和差异格式检查。

### 实现方案

- `build_runtime_tools()` 不再接收 Skill列表，仅依据 Runtime开关和执行上下文创建 `ExecutePython`。
- Runtime任务配置只暴露 `INPUT_DIR`、`OUTPUT_DIR` 和 `INPUT_FILES`，不再注入 `RUNTIME_ARGS`。
- `code_executions` 仅记录执行上下文、代码摘要、资源状态和执行结果，不再区分 Skill脚本来源。
- 保留 Skill提示词、参考文件、HTTP Action等非脚本执行能力。

### 影响范围

- Runtime工具、执行服务、子进程配置和 Agent工厂。
- `code_executions` 数据库表结构。
- Runtime相关文档和测试。

### 实现结果

- 已删除 `RunSkillScriptInput`、`RunSkillScript` 工具注册及 Skill 脚本路径解析逻辑。
- `build_runtime_tools()` 已简化为只接收 `RuntimeContext`，Runtime 开启时只注册 `ExecutePython`。
- Runtime 子进程不再读取 `arguments` 配置，也不再向用户代码注入 `RUNTIME_ARGS`。
- `code_executions` 新表结构和现有数据库迁移均已删除 `source_type`、`skill_id` 字段。
- README、Runtime 接口约定、Runtime 实现说明、Skill 集成说明和项目恢复文档已同步更新。
- 新增 4 项回归覆盖，确认工具注册开关、上下文校验和 `RUNTIME_ARGS` 下线行为。
- 后端完整 85 项测试、Python 编译检查和 `git diff --check` 均通过。

## 用户 API Key 与无状态聊天接口

### work_list

1. 新增用户 API Key 数据表、强类型实体、哈希生成、验证、轮换和吊销能力。
2. 增加仅允许平台 JWT 用户调用的 API Key 管理接口和前端管理入口。
3. 新增基于 `X-API-Key` 鉴权的外部聊天接口，通过密钥解析当前用户。
4. 定义外部聊天消息实体和校验规则，不接收平台 `session_id`，由调用方提交完整历史。
5. 抽取平台聊天与 API 聊天共用的 Agent 准备和流式执行逻辑。
6. 平台聊天继续维护 `chat_sessions/chat_messages`；API 聊天不写入这两张表。
7. 为 Trace 增加 `platform/api/workflow` 调用来源，并保持模型 Token 限额对 API 调用生效。
8. 补充外部接口文档、API Key 安全测试、请求校验测试和聊天持久化边界测试。
9. 执行后端完整测试、前端构建、Python 编译检查和差异格式检查。

### 实现方案

- API Key 使用 `ap_live_<key_id>.<secret>` 格式，数据库只保存完整密钥的 SHA-256 哈希。
- API Key 明文只在创建或重新生成时返回；重新生成后旧密钥立即失效。
- 外部接口使用独立认证依赖，仅开放明确标记的接口，不继承平台管理权限。
- API 请求只允许 `user`、`assistant` 消息，最后一条必须是 `user`，并限制消息数量、单条长度和总长度。
- 外部调用每次生成独立请求 ID、LangGraph thread ID 和 Runtime workspace，不复用服务端会话状态。
- `trace_runs.invocation_source` 作为调用来源事实字段；API 历史不进入平台消息表。

### 影响范围

- 用户 API Key 数据库表、认证服务和管理接口。
- 聊天运行实体、聊天服务、外部 API 路由和应用路由注册。
- Trace 表结构、Trace 查询和工作流 Trace 来源。
- 用户菜单中的 API Key 管理界面。
- README、外部调用文档和自动化测试。

### 实现结果

- 新增 `user_api_keys` 表，每个用户维护一条 API Key 记录，完整密钥只在签发时返回一次。
- API Key 使用高强度随机 secret，数据库仅保存 SHA-256 哈希；支持查询脱敏状态、轮换和吊销。
- 用户菜单新增 API Key 管理弹窗，可生成、复制一次性明文、重新生成和吊销密钥。
- 新增 `/api/v1/agents/{agent_id}/chat/stream`，通过 `X-API-Key` 安全方案解析用户。
- 外部接口不接收 `session_id`，只接受严格校验的 `user/assistant` 历史，且不写平台会话和消息表。
- 平台聊天和 API 聊天已复用同一 Agent 准备与流式执行核心，平台原有消息持久化保持不变。
- Trace 已记录 `platform/api/workflow` 来源和可选客户会话标识，Trace 页面可以直接查看来源。

## 外部请求 ID 持久化

### work_list

1. 为 `trace_runs` 增加可空且唯一的 `request_id` 字段。
2. 将外部聊天路由生成的请求编号传入 Trace 上下文并在运行开始时落库。
3. 在 Trace 列表和详情接口中返回请求编号，为问题排查和反馈关联提供查询入口。
4. 补充数据库迁移、专项测试和外部 API 文档。
5. 执行后端测试、Python 编译检查和差异格式检查。

### 实现方案

- 外部 API 继续在路由层为每次请求生成一个 UUID，并通过响应头 `X-Request-ID` 返回。
- 同一个编号经聊天准备服务传入 `TraceContext`，创建 `trace_runs` 时写入 `request_id`。
- 唯一索引保证一个公开请求编号最多关联一条 Trace；MySQL 允许多条 `NULL`，因此平台聊天和工作流不受影响。
- `request_id` 只用于请求追踪和后续反馈关联，不承担认证或会话记忆职责。

### 影响范围

- `trace_runs` 数据表定义和启动迁移。
- 外部聊天准备链路与 Trace 上下文。
- Trace 查询接口、外部 API 文档和专项测试。

### 实现结果

- `trace_runs.request_id` 已增加为 `VARCHAR(64) NULL`，并建立唯一索引 `uk_trace_runs_request_id`。
- 外部聊天生成的请求编号已原样传入 `TraceContext`，Trace 开始时与输入、模型和调用来源一起落库。
- 平台聊天和工作流的 `request_id` 保持为空，不改变原有会话与工作流执行逻辑。
- Trace 列表和详情接口已返回 `request_id`，后续反馈接口可以直接使用该编号定位生成记录。
- 当前数据库迁移执行成功，并确认字段类型、可空约束和唯一索引均符合设计。
- 新增请求编号写入与服务层透传测试；后端完整 97 项测试、Python 编译和 `git diff --check` 均通过。

## Agent 显式任务规划

### work_list

1. 为 Agent 增加默认关闭的 `disabled/explicit` 任务规划模式。
2. 新增任务计划和步骤实体、数据库表及 Trace 关联查询。
3. 构建“生成计划、顺序执行步骤、最终汇总”的外层 LangGraph。
4. 每个步骤复用现有 ReAct、Skill、MCP、Python Runtime 和模型 Token 限额能力。
5. 增加计划创建、步骤开始、步骤完成、步骤失败和计划完成 SSE 事件。
6. 在聊天页实时展示计划，在 Trace 详情展示持久化计划和步骤结果。
7. 隐藏规划模型原始 JSON，只把最终汇总识别为正式回答。
8. 在客户端断开、流异常、结构化校验失败和空响应时回收活动计划。
9. 更新 README、外部 API 协议和专项测试，并执行完整验证。

### 实现方案

- 规划模式保存在 `agents.planning_mode`，旧 Agent 和新 Agent 均默认 `disabled`。
- 显式规划只用于普通平台聊天和外部 Agent API；工作流已有用户定义节点，不重复嵌套规划图。
- 外层 StateGraph 固定为 `create_task_plan -> prepare_plan_step -> execute_plan_step -> finalize_plan`，步骤之间严格串行。
- 规划模型最多生成 6 个结构化步骤；JSON 无法解析时退化为单步骤计划，避免请求直接失败。
- 步骤执行继续使用原 ReAct 子图，最终汇总才应用 Agent 的结构化输出 Schema。
- 计划和步骤写入 MySQL，并通过 `trace_run_id` 与 Trace 一一关联；LangGraph State 用于本次图执行中的状态传递。
- 规划 JSON 不作为 SSE 文本发送；页面只消费解析后的计划事件。
- 异常回收把运行步骤标为 `failed`、待执行步骤标为 `skipped`，避免数据库长期保留 `running` 状态。

### 影响范围

- Agent 配置实体、接口、数据库字段和前端表单。
- Agent 工厂、自定义 State、聊天流式聚合和 LangGraph 执行链路。
- 任务计划持久化、Trace 详情接口与聊天/Trace 页面。
- 外部 Agent API 的 SSE 事件协议、README 和自动化测试。

### 实现结果

- Agent 已可按配置选择关闭或启用显式规划，默认行为与原聊天兼容。
- 启用后会先生成有限计划、逐步复用现有工具执行，并只输出一次最终汇总答案。
- 计划、步骤、结果和错误已持久化并可在聊天页及 Trace 详情查看。
- 规划过程新增 5 类 SSE 事件，规划模型原始 JSON 不再显示为执行说明。
- 断连和异常路径会自动结束活动计划，保留已完成步骤并跳过未执行步骤。
- 工作流 Agent 不会嵌套显式规划，避免与已有工作流节点发生双重编排。
- 后端完整 101 项测试、Python 编译、Node 20 前端生产构建和 `git diff --check` 均通过。
- 当前 MySQL 已完成迁移，并确认 `agents.planning_mode`、两张计划表及唯一索引存在。
- 新版服务已在 `20005` 端口启动，OpenAPI 请求返回 HTTP 200，公开 Schema 包含 `planning_mode`。
